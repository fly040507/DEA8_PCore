# B侧统一列流与接口契约

依据：用户2026-09-17提供的《AI工具意见.docx》，结合现有RTL及仿真结果。
本文描述本次实际落地内容，覆盖先前的256项KVFIFO及HBM双WFIFO内部结构。
本次没有修改其他同学的真实GCore、VPU、SFU或HBM控制器；这些接口要求仍需联合确认。
最终67模式回归与综合证据见 [验证记录](B侧统一列流验证记录_20260917.md)。

## 1. 实现范围

| 事项 | 当前实现 |
| --- | --- |
| BEntry | 128bit列向量+8bit共享scale，共136bit |
| KVFIFO | 独立64项，只存BEntry，不存协议元数据 |
| WFIFO | 另一独立64项，同一FIFO模块，不与KV共享存储 |
| FIFO读口 | 同步RAM读取、缓存队首、首项旁路寄存，非异步RAM读 |
| KVB校验 | RX入口校验后入队；错误锁存并阻止继续收发 |
| HBM内部适配 | 一份Tile Assembler，行主序8+1beat转换为16项列流 |
| 列写入 | W/KV使用同一个列写入数据通路模块 |
| Bank控制 | W的Stationary Loader与Attention的Matrix Sequencer仍各自管理本路径 |
| Attention调度 | 保留跨Job预加载、稳态828拍及PV53后独立828拍尾部槽 |

“共享列加载模块”指模块逻辑复用，不表示已实现完整PCore中W/KV二选一的物理MUX、仲裁或统一Top。
当前两条路径分别在不同引擎中验证，不允许将两个状态机同时接到同一组PE控制端。

## 2. 物理数据路径

```text
HBM valid/ready/data[255:0]
  -> W Tile Assembler: W[16][16] + E[16]
  -> W FIFO: 64 x {data128, scale8}
  -> Stationary Loader: 预留16项 + bank/column状态
  -> B Column Loader -> PE权重Bank A/B + 外部E_STAT Bank A/B

GCore KVB: payload + 协议字段
  -> RX校验/顺序计数 -----> KV_MASK[55]及epoch/valid
  -> KV FIFO: 64 x {data128, scale8}
  -> Matrix Sequencer: current/next Job + bank/column状态
  -> B Column Loader -> PE权重Bank A/B + 外部E_STAT Bank A/B

激活Q_ACT_REG -> INT8乘法 -> 四级加法树 -> Psum_out_reg
scale/tag旁带 -------------------------------> DEQACC
```

数据与scale共用一次valid/ready握手，没有独立pop、独立计数或错位补偿。
`b_entry_t`为packed struct：`[135:8]=data`、`[7:0]=scale`。
其中`data[8*k+:8]`写入PE[k][column]，k=0..15。
加载column=c时，16个PE的权重及E_STAT[bank][c]在同一时钟沿更新。
scale仍在PE外；这里改变的是加载方式，不改变MXU/DEQACC的反量化数值定义。

## 3. HBM接口与单Tile重排

外部每Tile仍为9个256bit beat：前8个是16行INT8权重，最后1个的低128bit为16个scale。
每个权重beat包含两行，每行16个INT8；高/低半字及元素顺序按原HBM协议不变。
scale beat高128bit忽略；scale[n]对应输出列n，不是输入行k。

Assembler实际保存256字节权重和16字节scale，共272字节有效数据，另有计数器和状态位。
收完scale后才拉高列流out_valid，按column=0..15输出，每列16个权重+1个scale。
排出期间hbm_ready=0；最后一列握手后，下一拍才允许接收下一Tile。
因此无停顿时服务时间为9+16=25拍/Tile，不是持续9拍/Tile，也不是全速无限接收HBM。
25拍是Assembler接收/排出服务时间，不包括FIFO预留和Bank装载等冷启动延迟。

HBM源必须在valid=1且ready=0时保持当前beat，直到握手；固定节奏且不可背压的源不能直接连接。
W FIFO装满或下游未释放Bank时，背压可经Assembler继续传到HBM。
W Stationary Loader等待至少16项，保证启动后16拍完整装载；延迟scale时不会写入不完整Tile。
Assembler与FIFO可同步clear，但当前W_Loader仅接硬复位、clear绑0；不宣称已实现W Job取消/重启协议。

## 4. GCore到PCore契约

一次Attention Top启动锁存head/epoch，并清空接收计数、错误状态、mask有效位和KVFIFO。
GCore应配合发送本head的完整有序流；当前KVB每项含epoch但不含head，不能混入其他head。
Top启动通知如何与真实GCore调度接线，仍是完整PCore集成工作。

| 端口字段 | 位宽 | 含义 |
| --- | ---: | --- |
| kvb_q | 128 | 16个INT8，归一化后的B矩阵一列 |
| kvb_e | 8 | 本列沿归约轴16元素共享的scale |
| kvb_kind | 1 | 0为QK的K，1为PV的V |
| kvb_blk_id | 6 | 逻辑Block编号0..54 |
| kvb_feat_blk | 4 | 本矩阵Job的Tile索引0..15 |
| kvb_key_lane | 4 | 统一解释为Tile内输出列编号0..15 |
| kvb_valid_mask | 16 | 此逻辑KV Block的有效key掩码 |
| kvb_last | 1 | 每个矩阵Job的第256项置1 |
| kvb_epoch | 4 | 必须等于启动时锁存的epoch |
| kvb_valid / ready | 各1 | 同沿为1才接收并推进计数 |

外部有效内容总宽度为172bit，但FIFO只保存其中136bit payload。
其余36bit在入口校验并转为状态，不随每项向Loader传递。
这些是本PCore接收端要求，不等于真实GCore已按该协议实现或完成双方签字确认。

固定Job顺序：QK0、QK1、PV0、QK2、PV1、...、QK54、PV53、PV54。
共110 Job；每Job16 Tile，每Tile16列，总计28160次接收握手。
RX自身的job/entry计数跟随接收推进，不等待矩阵消费；FIFO维持有序，Matrix端按相同顺序消费。
不得乱序、交错其他head/epoch、跳项或重复项。
收到28160项后ready保持低；已入队数据仍可继续排空，不能提前关闭消费端。

QK：B[k,n]=K[block*16+n, tile*16+k]，scale按每个key的16个feature共享。
PV：B[k,n]=V[block*16+k, tile*16+n]，scale按每个feature的16个key共享。
因此PV列格式不能直接拿按feature方向量化的V缓存假装等价；上游必须提供约定方向的数据及scale。

RX校验kind、block、epoch、Tile、列号、last、mask一致性及尾部padding位。
同一Block在QK和PV中出现时，mask必须一致；logical_seq=867，尾Block仅前三个key有效，其余13bit不得置1。
mask在RX握手时写独立表，不必等到FIFO消费；表读按block/epoch查询。
当前实现不检查padding位置的数据是否为0，掩码本身与后续Mask/P处理负责屏蔽，不能把该检查描述为padding数据校验。

当valid呈现非法事务时，即使FIFO满也会检查：该项不入队，protocol_error锁存，仿真触发fatal。
这是严格fail-stop契约，不是允许源先放无效元数据、等ready再修正的协议。
错误后应整体中止并重新启动Top，同时重置矩阵/上游上下文；不要只清一个FIFO后继续旧矩阵Job。
start为同步clear，RAM内容不清零，通过指针、count和valid使旧内容不可见。

## 5. FIFO容量与实现

默认深度64，共4个Tile；单FIFO有效容量64×136=8704bit=1088字节。
两份独立FIFO共2176字节有效数据，加W Assembler为2448字节；这不包括Bank、mask、计数器、头缓存或其他PCore存储。
逻辑64项已包含缓存队首，不能算作65项。RAM与头寄存器在物理上可能保存同一项的副本。

普通pop时同步预取下一RAM地址；空队列首push和仅剩一项时pop+push使用输入旁路寄存器。
满队列可同拍pop+push；不覆盖还未消费的项；out_valid=1但out_ready=0时队首保持。
存储阵列和RAM读寄存器不做复位，指针/count/control复位；无组合RAM读，利于BRAM推断。

Vivado2022.2对单个64×136 FIFO、代表器件xcu280-fsvh2892-2L-e进行OOC综合：
2个RAMB36E2、173 LUT、156 FF、0 DSP，无LUT RAM、无Latch。
这是单实例综合结果，不是整个设计资源，也不是所有综合设置下的不变数字。
深度很浅而总线很宽，BRAM利用率偏低，不能将8704bit有效容量直接当作物理BRAM用量。
综合警告包括package参数按localparam处理、未启用并行综合及OOC缺少HD.CLK_SRC；没有Critical Warning/Error。
脚本4ns时钟只是分析约束，未做布局布线，也不证明全系统达到250MHz。

64项是否够用取决于GCore服务延迟与背压契约。现有充分供数测试保持828拍，但不能保证任意外部断供仍满足预算。
FIFO_DEPTH可调；W路径至少要容纳一个完整Tile，修改参数后需重新仿真/综合。

- `rtl/dea8_matrix_engine.sv`、`dea8_qk_engine.sv`：接列流，保持MXU算术及DEQACC接口。
- `tb/tb_dea8_b_fifo.sv`：随机背压、回绕、满交换、单项旁路和同步清空。

- `tb/tb_dea8_attention_matrix.sv`：矩阵数值/时序和8种KVB协议错误注入。

旧`dea8_dualwrite_fifo`、`dea8_hbm_tile_unpack`、`dea8_tile_columns`保留作历史参考，不在当前W/Attention主链实例化。
旧KVB Adapter和外部GCore stub仍有独立兼容测试；其中V_UNCONFIRMED用例不是新连续KVB协议的签核结论。
Python旧Loader模型保留历史首拍scale行为，不作为本次新列流的逐拍参考。新路径以RTL专门测试及完整矩阵数值检查为依据。
本次不改完整Attention数学行为模型：真实SFU/VPU仍待同学交付，行为模型不能代替真实模块精度/时序验收。
