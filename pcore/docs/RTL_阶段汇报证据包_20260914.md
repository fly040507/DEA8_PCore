# DEA-8 PCore RTL 阶段汇报证据包

## 1. 汇报结论

当前已经完成并验证的是 PCore 的矩阵计算主链、DEQACC、Attention 调度与本地存储协同，以及 GCore 到 PCore 的 KVB/XBC 前端适配。

已经贯通的主要数据链为：

`HBM/KVB -> Stationary Loader -> 16x16 MXU -> DEQACC -> FACC_A/B 或 OACC`

Attention 控制链已经能够执行 55 次 QK 和 55 次 PV，并调度 QK_POST、P_EXP、P_POST、OACC_SCALE、RECIP 和 A_FIN。KVB 前端能够保存完整事务、检查 Job Context、维护 KV_MASK，并把有效 key mask 送到 VPU_QK_POST 接口。XBC 前端已经完成 256-bit 到两组 128-bit MXINT8 事务的拆分与背压验证。

当前结果属于 RTL 功能与位精确仿真阶段。尚未完成目标 FPGA 综合、资源利用率和时序签核；VPU/SFU 当前使用接口测试壳，因此不能宣称完整 Softmax 和 A_FIN 的 FP32 数值已经在系统 RTL 中签核。

## 3. 建议汇报页与现场证据

### 第 1 页 当前完成范围

画出主链：

`XBC/KVB/HBM -> Frontend/Loader -> MXU -> DEQACC -> FACC/OACC -> VPU/SFU 接口`

口头说明：本阶段不是只写了单个乘法模块，而是完成了从数据进入、矩阵计算、反量化累加，到 Attention 调度和外部模块接口的可仿真闭环。

现场证据：展示 `dea8_pcore.f` 的模块列表和 GitHub 提交 `2c3fc02`，说明本次汇报对应固定版本。

### 第 2 页 MXU 与 DEQACC

展示 16x16 PE、W_BANK_A/B、Q_ACT_REG、四级加法树、Psum_out_reg 和 sideband，再接 DEQACC L0-L4。

关键数字：

- 256 个 PE。
- 16 拍首 Tile 权重加载。
- 16x51=816 拍连续计算。
- 供数充分时每 Block 共 832 拍。
- DEQACC 为 L0-L4 五级，L4 为实际写回提交。

现场证据：展示 `tb_dea8_mxu PASS`、`tb_dea8_deqacc PASS` 以及测试中的 832 拍断言。

### 第 3 页 数值正确性

重点不要只放 PASS，要解释比较方法：Python 参考模型先生成黄金向量；XSim 驱动 RTL；测试平台对每个实际 RAM 写回结果逐位比较，任一位不一致立即 `$fatal`。

可报告的数据量：

- Matrix Engine：3264 个 512-bit 输出向量逐位比较。
- MXU 主链：2 Block、32 Tile、1632 行、26112 个 lane。
- DEQACC：100225 组 FP32 加法参考案例、51568 组反量化参考案例；流水提交 3433 个 16-lane 向量，即 54928 个 lane。
- Python 单元测试：20 项。

现场证据：展示 `mem_wr_data !== golden[writes]` 的测试代码和最终 PASS 输出，形成“比较机制 + 比较规模 + 通过结果”的完整证据。

### 第 4 页 Attention 调度与存储

展示 QK(b+1) 与 PV(b) 交替、FACC_A/B、SBUF/PBUF ping-pong、OACC、alpha_A/B 和 m/aa/l/recip_l。

关键验证：

- 55 次 QK 和 55 次 PV 的真实矩阵 Job 已执行。
- 54 次 OACC_SCALE，与第一轮无旧 OACC、后续 54 轮缩放的算法关系一致。
- 408 对 P 流通过生产端和消费端随机背压。
- FACC/OACC 的完成依赖实际 commit，不把命令接受或最后输入误当成写回完成。

必须同时说明：VPU/SFU 壳只模拟延迟和接口操作，尚不代表 EXP、Mask、RowMax、量化和 A_FIN 的完整 FP32 算法 RTL 已实现。

### 第 5 页 XBC/KVB Frontend

KVB 证据链：

`GCore KVB -> 172-bit 完整事务 KVFIFO -> Expected Matrix Context -> normalized B-column -> Matrix Engine`

说明数据与 q/e/kind/block/column/tile/mask/last/epoch 一起入队和出队，避免数据与 scale 或上下文失配。允许下一 Block 停留在 KVFIFO，但不会越过 Matrix Job Context 进入 Stationary Bank，因此没有破坏 832 拍 Block 边界方案。

XBC 证据链：

`256-bit Data + 2 Scale -> XFIFO -> slot0/slot1 -> 2 x (128-bit + 8-bit scale)`

现场证据：展示 KVB 与 XBC 正向 PASS；再展示至少三项错误注入，例如 BAD_EPOCH、EARLY_LAST、MASK_CHANGE，说明设计不仅能处理正确输入，也能阻止错误事务污染计算链。

### 第 6 页 当前边界与下一步

已完成：RTL 功能、位精确参考比较、协议/背压/复位/错误注入、55 Block 调度闭环。

未完成：

- V 模式 `kvb_key_lane` 的最终 GCore 编码确认，当前 RTL 使用显式保护参数。
- XBC 后面的通用 Projection Sequencer。
- 完整 PCore Top、正式 CNET 与 HBM 系统接口。
- 真实 VPU/SFU 算法 RTL 替换接口壳。
- 完整 Attention FP32 数值签核。
- Vivado 目标器件综合、DSP/BRAM/URAM 利用率和时序报告。

建议下一步的硬证据是综合报告和真实 VPU/SFU 联调，而不是继续增加只验证接口计数的测试。

## 5. 导师可能追问的问题

### 832 拍是否是端到端延迟

不是。它是数据已准备时，从首 Tile Bank Load 到最后一次矩阵乘法发射的资源占用预算：16+16x51=832。首次 KVB/HBM 到达、Job 握手、流水排空、DEQACC 最后提交和外部 VPU/SFU 延迟都不在这个数字中。

### 55 对 QK/PV PASS 是否证明 FlashAttention 数值完全正确

不能。它证明调度、矩阵计算、存储访问和接口依赖贯通；真实 VPU/SFU 尚未替换 Stub，因此 EXP、RowMax、在线 Softmax 更新及最终归一化仍需完整 FP32 数值验证。

### 为什么预期失败也算证据

因为这些用例故意输入错误协议或制造资源冲突。仿真只有在指定断言准确触发时才判为 PASS，可证明保护逻辑实际生效，而不是源代码中仅存在一条未被覆盖的断言。

### KVB 预取是否破坏每 Block 额外 16 拍

不破坏。预取只允许进入 KVFIFO；Stationary Loader 仍是 W_BANK_A/B 的唯一 Owner。下一 Block 的 Tile0 不会在当前 Block Tile15 期间跨边界装入 Bank。

### 当前最有价值的下一步证据是什么

第一是把 VPU/SFU 的真实实现接入并做完整 Attention 数值对比；第二是指定目标 FPGA 运行综合，得到 DSP、LUT、FF、BRAM、URAM 和 WNS/Fmax 的工具报告；第三是组装正式 PCore Top 后做端到端协议回归。
